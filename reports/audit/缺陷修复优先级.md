## 1. 先校正五条口径（按代码核对）

用户给出的缺陷前提里有几条与代码实际不符，直接影响排序，先纠正：

### 1.1 Office 多开不是「卡在准入闸」

- 准入门槛确实存在：`src/javascripts/os-api.js:158-159`、`src/javascripts/plugin-manager.js:707-709`、`:849-850`。
- 但 Office 已声明 `"multiWindow": true`：`mods/office/manifest.json:7`。
- 因此多开**已经放行**，`mods/office/script.js:10`、`:291` 也在用 `newWindow`。
- 真实缺口是：其他应用未声明、`⌘N` 未全面接入、实例状态隔离需逐应用验证。**这不是「先放开内核闸」的任务，而是「逐应用适配」的任务**，成本从 XL 降到按应用计的 M。

### 1.2 照片外部文件夹挂载已落地，但只活一个会话

- 挂载实现完整：`mods/photos/photo-store.js:91-92`（`externalMounts` 注释明确「会话内有效」）、`:103-150` 扫描与 `ext://` 解析、`mods/photos/index.html:85` 入口按钮。
- 缺的是**持久化**：`FileSystemDirectoryHandle` 没有存进 IndexedDB，刷新即失效。
- 所以修复动作是「把 handle 持久化 + 启动时请求恢复权限」，不是「从零做挂载」。

### 1.3 菜单闪光与 Dock 弹跳都已入库，不是「正在改未入库」

- 菜单闪光：`src/javascripts/ui/menuFeedback.js:38-60` 的 `pressMenuItem()`，90ms 按下态；已被 25 处调用（`ui/menu.js:19`、`ui/contextMenu.js:118`、`finderbar.js:775`、`mods/notepad/script.js:426`、`mods/safari/js/menus.js:52` 等）。
- Dock 弹跳：`src/javascripts/dock.js:227`、`:264-280`、`:464-553`。
- 唯一没接入的是 Office 功能区：`mods/office/ribbon.js:68-80` 直接 `createElement("select")`，`:212-214` 直接监听 `change`，没有走 `pressMenuItem`。
- 这一批里真正「未入库/未验收」的只有 Office 外观四项（强调色 `mods/office/style.css:5/29-32`、选项卡横向滚动 `ribbon.css:21-22`、纸张直角与背景 `view-word.js:1954-1973`、苹果名称 `manifest.json` + 四语包）——代码在工作区已存在，属于「已写完、待验收提交」。

### 1.4 genie 的根因不是「抓帧频率不足」，而是原生截图根本不可用

- `src/javascripts/wm/genie-effect.js:195-198` 写得很明确：本扩展未申请 `activeTab` / `<all_urls>`，`captureVisibleTab` **必然失败**并进入 60s 冷却，实际唯一可用的是 DOM 快照。
- 慢放阶段靠几何插值：`src/javascripts/wm/genie-geometry.js:176-188`（`easeOutCubic`），材质仍是单张静态快照，由 GLSL 变形（`genie-renderer.js:48-76`）。
- 所以「提高抓帧频率」在当前权限下做不到；要先决定是**加权限**还是**改走高质量 DOM 快照**。

### 1.5 体积数字与仓库实测吻合

- 内核 JS 模块 92 个；`mods/` 14 个插件、442 个文件；`assets/` 6641 个文件（合计约 7175，加根文件约 7179）。
- 体积大头：`assets/icons` **54.3MB / 204 个文件**（整套 macOS 应用图标，多数未被引用）；`assets/svgs` **14.6MB / 6286 个文件**（编号式 SF Symbols 全量）；`images` 5.1MB、`fonts` 2.5MB、`devices` 1.8MB、`cursors` 1.3MB、`brand` 1.0MB。
- 结论：82.5MB 里约 **69MB 是「整库拷入、按目录全量打包」造成的**，不是业务代码大。

## 2. 缺陷卡

### A. 结构性问题

#### A1 插件不是真沙箱

- **问题**：插件脚本与界面注入宿主主文档执行。`plugin-manager.js:738` `document.body.insertAdjacentHTML("beforeend", htmlText)`；HTML 只做可执行内容剥离（`:186-195`），脚本仍是同源 `<script>`。`caller-context.js:70`、`:109` 的 `claimCaller`/`runAs` 与 `osfs.js:209` 的 `boundaryKey` 只能防「调错 API」，防不住「直接摸 `document`、读 localStorage、发请求」。
- **影响谁**：安装第三方插件的终端用户；插件审核者；后续所有插件开发者（一旦改沙箱，入口写法会变）。
- **不修的后果**：任一插件被投毒即可读走全部桌面数据（`.DS_Store`、照片库元数据、设置），且没有任何事后隔离手段——属于「出了事没法收拾」。
- **修复成本**：
  - 止血版（P0）：收紧危险 API 白名单、安装来源校验、注入前 CSP/`trustedTypes` 级检查 → **M，`plugin-manager.js` + `os-api.js` + `store-api.js` 约 150–250 行**。
  - 真沙箱（P1）：插件放进独立 iframe/worker，改消息桥、改 14 个插件的入口与 `Deskly` API 访问 → **XL，新建 1–2 个宿主机模块（约 600–900 行）+ 内核桥接 300 行 + 14 个插件适配 300–500 行**。
- **依赖**：止血版 → 真沙箱；真沙箱与 Office/照片的功能开发**互斥排期**（同一批插件会被两侧同时改）。

#### A2 体积 82.5MB / 7179 文件

- **问题**：不是代码膨胀，是资源整库打包（见 1.5）。
- **影响谁**：所有新装用户（下载、解压、首装等待）；走商店时的审核与包体限制；CI 产物传输。
- **不修的后果**：首装成本高、商店可能直接拒包；每次构建多传 80MB，发布迭代变慢。
- **修复成本**：**S–M，代码 0 行，新增一个资源裁剪脚本约 80–120 行**；难点在引用扫描（`manifest.json` 图标、`office-brand.js`、`paths.js` 的字符串拼接图标名要人工复核）。
- **依赖**：无前置；必须在**任何大规模图标改造（任务 26 的 Phosphor 迁移）之前**做，否则会裁掉即将替换的旧图标，白做一次。

#### A3 只活在 Chromium

- **问题**：`backdrop-filter` 在样式表 10 个文件、101 处；genie 原生截图依赖 `chrome.tabs.captureVisibleTab`（`genie-capture.js:87-122`），Firefox/Safari 无此 API。
- **影响谁**：非 Chromium 用户；想把 Deskly 作为通用主页的用户。
- **不修的后果**：装了也白屏或严重掉质感；支持面被永久锁死。
- **修复成本**：
  - 方案一（推荐先做）：**明确声明 Chromium-only**，安装页与 README 写清 → **S，0 行代码**。
  - 方案二：做降级——模糊令牌已有集中层（`surface.js` 的 `--surface-*`），CSS 回退约 100 处但可批量；genie 已有 `nativeUsable()` 探测（`genie-capture.js:88`）→ **L，主要风险在测试面（需真机三浏览器）**。
- **依赖**：方案二依赖 A2（先裁资源，否则每次跨端验证都拖 82MB）；不依赖 A1。

#### A4 无构建步骤

- **问题**：`package.json:5` 明写「no build step」；92 个内核模块 + 插件脚本全部按原生 ESM 冷启动请求。
- **影响谁**：首屏等待敏感的用户；弱网/低端机。
- **不修的后果**：冷启动请求数随模块数线性上涨，后续每加功能都更慢；HTTP/2 也压不住模块图深度。
- **修复成本**：引入 esbuild（或 rollup）单入口打包 + 保留插件动态加载 → **M，1 个构建脚本 + `package.json` scripts + 改 index/sw 入口引用，约 150–350 行**；风险点是动态 `import()` 路径与插件缓存戳（`plugin-manager.js:274-320` 的 `scriptPrefetch`/`scriptSeq`）必须保留。
- **依赖**：A2 → A4（先把 80MB 静态资源剔出去，打包收益才看得见）；A4 与 A1 真沙箱有冲突（沙箱会改入口形态），**要么先 A4 再沙箱，要么沙箱后重做打包配置**。

- **依赖**：母版 → 幻灯片编号（P3 依赖版式占位符链，`features.md:49`）；图表/SmartArt 与 B2 条件格式都依赖「规则/数据求值」公共能力，**可合并成一条公共底座先做**。

#### B4 存储与访达

- **问题**：
  1. 只有自建文件系统，碰不到真实磁盘（`osfs.js` 顶层目录为虚拟路径）；
  2. 照片导入不压缩（`mods/photos/script.js:2507` 原文件直传；`photo-store.js` 无重编码）；
  3. 索引表只是在 localStorage 存元数据（`mods/photos/script.js:1`、`:425-530`）；
  4. 外部挂载只活一个会话（`photo-store.js:91-92`）。
- **影响谁**：把 Deskly 当文件管理器用的用户；照片库体积敏感的用户。
- **不修的后果**：照片库无上限膨胀、刷新后外部目录消失、文件管理器只能玩「沙盒里的玩具文件」。
- **修复成本**：
  - 外部挂载持久化：**M，`photo-store.js` 约 150–250 行**（handle 存 IndexedDB + 权限恢复）。
  - 照片压缩：**S–M，导入链路 80–150 行**（canvas/offscreen 重编码 + 质量参数）。
  - 索引表落 IndexedDB：**M，150–250 行**。
  - 真实磁盘：**不是代码问题，是平台边界**。Chrome 扩展只能在用户手势下拿 `FileSystemDirectoryHandle`；要系统级访问必须做 native host，成本 **XL 且超出当前项目形态**。建议明确写进文档「只支持用户授权目录」，不排期。
- **依赖**：压缩与索引先做（数据模型变化），再做外部挂载持久化（要按新索引落盘）；真实磁盘不进排期。

#### B5 键盘可访问性（菜单无方向键）

- **问题**：`src/javascripts/ui/menu.js` 对 `Arrow*`/`keydown`/`role` 检索无命中；`src/javascripts/core/menuProviders.js:99-109` 只监听 `Alt` 切换菜单栏。桌面图标有方向键（`desktop.js:848`、`:893`），菜单没有。
- **影响谁**：键盘用户、无障碍用户；也是 Office 自绘下拉的前置能力。
- **不修的后果**：菜单只能鼠标点，键盘用户无法完成「新建/打开方式/删除」等操作。
- **修复成本**：**M，`ui/menu.js` + `ui/contextMenu.js` + `core/menuProviders.js` 约 200–350 行**（roving tabindex、`aria-activedescendant`、Esc 分层退出与现有 Quick Look 的 Esc 语义要对齐）。
- **依赖**：无前置；**它是 C4（Office 功能区自绘下拉）的前置**。

#### B6 genie 抓帧与慢放

- **问题**：见 1.4。原生截图在本扩展权限下必然失败；慢放靠几何插值，材质是单张静态快照。
- **影响谁**：所有用户（这是第一眼观感）。
- **不修的后果**：窗口里正在播放的视频/滚动内容在缩小动画中「冻住」；越慢放越假。
- **修复成本**：
  - 路径一：加 `<all_urls>` 或 `tabs` 权限，让 `captureVisibleTab` 可用 → **S 代码（`manifest.json` 1 行 + `genie-capture.js` 已有逻辑），但隐私面与商店审核风险显著上升**。

- **依赖**：与 A3 共用「权限决策」；若选路径一，会同时缓解 A3 的一部分（但仍不解决 Firefox）。

## 3. 总顺序与理由

排序不是按「严重度」单向排，而是按三条规则：

1. **不可逆损失优先**——数据丢失（B1）、发布断链（C3）、安全事故（A1）没有「以后再说」的余地；
2. **能解锁别的项的先做**——C3 解锁所有发布；D1 清理工作区；B5 解锁 C4；B1 止血解锁 B1 完整建模；
3. **同期只动一条大链路**——A1 真沙箱会改插件入口、B1–B3 会改 Office codec、A4 打包会改入口形态，三条不能同时改同一批文件。

推荐总顺序（括号内为档位）：

1. **C3 扩展 ID**（P0）— 10 分钟、0 行代码，但不做则后面所有发布都白做。
2. **D1 工作区批次验收入库**（P0）— 0 行新代码，先把「已写完」变成「已交付」，同时让后续 diff 干净。
3. **B1 止血：Office 保存前备份 + 未建模部件告警**（P0）— 唯一一条会毁用户原文件的问题，代码量中等，必须最先堵。
4. **A1 止血：插件危险 API 收紧 + 来源校验**（P0）— 安全事故无事后手段，先用 150–250 行把「最坏情况」压到可收拾。
5. **A2 资源裁剪**（P0/P1 视分发方式）— 82.5MB → 目标 15MB 以内；越早做，后续每次验证越省。
6. **C1 待协调缺陷**（P1）— 其中 BUG-02/09/60 先做（涉及落点与读取），其余按模块批量清。
7. **B5 菜单键盘导航**（P1）— 解锁 C4，且是独立小闭环。
8. **C4 Office 功能区自绘下拉**（P1）— 紧接 B5，同一批组件。
9. **B4 照片压缩 + 索引落库 + 外部挂载持久化**（P1）— 数据模型一次改完，避免二次迁移。
10. **B6 genie 权限决策 + 快照保真**（P1）— 先决策权限，再动代码；与 A2 并行。
11. **A4 构建/分包**（P1）— 在 A2 之后，收益才可见；必须避开 A1 真沙箱窗口。
12. **B1/B2/B3 完整建模**（P1→P2）— 大工程，按文稿 → 表格 → 演示串行，共用「未建模部件检测」。
13. **A1 真沙箱**（P1，独立长线）— 与 9–12 并行会冲突，建议单独排一个窗口。
14. **A3 跨浏览器**（P2）— 先做「明确 Chromium-only」的零代码方案；真降级等 A2/A4 稳定后。
15. **C2 宣传片**（P2）— 成品要基于修完的版本拍，否则宣传的是带缺陷的界面。

**为什么不是「影响面 × 成本」简单排序**：C3 影响面极大但成本近乎零，理应第一；A1 真沙箱影响面最大但成本 XL，且会阻塞其它三条链路，所以只把「止血版」放 P0，完整沙箱单列长线；B1 完整建模影响面大但成本 XL，先用 M 级止血把不可逆风险消掉，再谈建模。顺序的核心是**先把「不可逆」变「可逆」，再把「大工程」拆成互不冲突的窗口**。

## 5. 并行与前置关系

**必须串行（有硬依赖）**

```
C3 → 任何发布
D1 → B1-a / A1-a（避免 diff 混线）
B1-a → B1-b
B1-b → B2 → B3（同一 codec 维护窗口）
B5 → C4
B4-a → B4-b → B4-c
A2 → A4
A1-a → A1-b；A4 与 A1-b 需先定入口形态，二者不可并行
C1-a → C1-b
```

**可以并行（不同文件树 / 不同验证面）**

| 并行组 | 说明 |
|---|---|
| C3 + D1 + A2 | 分别动 CI、工作区、静态资源，互不重叠 |
| A1-a 与 B1-a | 插件内核 vs Office codec，文件不交叉 |
| C1-b 与 B5/C4 | 前者是窗口/桌面，后者是菜单组件 |
| B4 与 B6 | 照片存储 vs genie 渲染 |
| A4 与 B5 | 构建脚本 vs 菜单组件；但只要 A1-b 未定，A4 配置可能返工 |

**建议的执行轨道**

- 轨道 1（发布与数据）：C3 → D1 → B1-a → C1-a → C1-b
- 轨道 2（体积与启动）：A2 → A4
- 轨道 3（安全）：A1-a（短）→ 单独窗口 A1-b（长）
- 轨道 4（可用性）：B5 → C4 → B4-a/b/c → B6
- 轨道 5（Office 能力）：B1-b → B2 → B3（必须等轨道 1 的 B1-a 完成）
- 轨道 6（对外）：A3 → C2（等前五条轨道的 P0/P1 收口）

## 7. 现在不要做的（避免白花成本）

1. **真实磁盘挂载**：Chrome 扩展没有系统级文件访问；只能在用户手势下拿目录句柄。做 native host 会改变项目形态，列入「不支持」，写进文档即可。
2. **在 A2 之前做 Phosphor 图标迁移**：会先把 54MB 旧图标换掉再裁，等于裁两遍。顺序必须是「裁资源 → 换图标」。
3. **在 B5 之前做 Office 自绘下拉**：会写一次鼠标版、再写一次键盘版。
4. **在 B1-a 之前做宣传片**：拍的是会丢用户格式的界面。
5. **在 A1 真沙箱之前大改插件 API**：沙箱会改入口契约；先小步收紧危险 API，再谈重写。

## 8. 一页结论

- **P0 六项**：扩展 ID、工作区入库、Office 保存止血、插件 API 止血、资源裁剪、三条落点缺陷。共同点：不做就会「装不上 / 升级断 / 丢文件 / 收不了场」。
- **P1 八项**：清账、菜单键盘、Office 下拉、照片三项、genie、构建分包。共同点：影响每天的使用手感与维护效率。
- **P2 六项**：真沙箱、Office 大功能、跨浏览器、宣传片。共同点：成本 XL 或依赖外部条件，必须等前面收口。
- **最先做的一件事**：配 `CRX_PRIVATE_KEY`。0 行代码，决定后面所有发布有没有意义。
- **最危险的一件事**：把含表格/脚注的 `.docx` 在 Deskly 里保存。B1-a 必须排在任何 Office 宣传或大规模试用之前。
