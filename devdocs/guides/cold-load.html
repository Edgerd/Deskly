冷加载机制

「启动只注册清单，点击才加载内容」的原理、缓存戳语义与两条硬约束。

两个阶段

阶段一：启动注册（仅清单）

plugin-manager.init()（bootstrap.js 调用）按 BUILTIN_IDS（13 个）逐个 fetch('./mods/{id}/manifest.json?v=' + VERSION) 建注册表，再从 IndexedDB 还原已安装 ZIP 插件， 最后派发 plugins-ready。程序坞监听它校准图标，启动台 / 商店据此渲染。 不加载任何界面 / 样式 / 脚本。首屏 Network 面板应看到 13 个 manifest.json 请求。

阶段二：点击加载（按需）

load(id) 按顺序拉三件（不是并行）：

  1. style.css → <link id="plugin-style-<id>"> 追加进 head，按 id 去重；
  2. index.html → fetch 后 insertAdjacentHTML("beforeend")；
  3. script.js → 每次先删旧脚本再注入新的（全新 URL）；
  4. 新 .window 交给 window-manager.manage() 绑行为，按 data-window / manifest 落实尺寸。

load() 自带并发去重（loadingMap）：同 id 加载中复用同一 Promise，连点不注两份。

缓存戳的真实语义（有意为之）

资源戳值语义
manifest.jsonVERSION随发布失效，同一发布内复用
style.css / index.html内置 VERSION；ZIP 安装 Date.now()已安装资源可被同 id 覆盖安装，必须每次取新
script.js（入口）永远 Date.now()入口顶层要跑 init()，URL 稳定会被 ES module 缓存命中 →「二次打开失效」

两条硬约束（代价：模块表不回收旧实例）

  1. 入口脚本每次重跑 → 它注册的全局资源（document/window 监听、定时器、轮询、window.__* 钩子、 __menuActions 键）必须在 plugin-unload 回调里释放。旧实例的监听不会随脚本元素移除而消失， 会永久累积。内置示范：finder / notepad / system-settings / photos 的 script.js 都有该监听。
  2. 被 import 的子模块只有一份实例（URL 稳定，跨打开复用）→ 入口的 init() 必须自己复位状态、 对订阅去重。不能假设「新实例 = 干净状态」。

卸载事件

事件detail语义
plugin-unload{id}单应用关闭 / 整个插件无存活窗口；移除 style 与脚本元素
plugin-app-unload{id, appId}多应用插件：关掉其中一个应用窗口（外壳仍在）
plugin-app-load{id, appId, windowName, el}多应用插件：每个应用窗口就绪（外壳只在第一个时注过一次）
plugin-app-open{id, appId, windowName, file}访达双击带文件打开；窗口已存在也派发（换文件复用窗口）
调试技巧 顶栏「调试 → 重载当前插件」= 关窗再开窗，专门用来验证你的 plugin-unload 是否清干净（重载后若界面叠了两层、菜单项多了，就是没释放）。
