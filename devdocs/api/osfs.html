文件存储 OSFS

整个桌面的文件系统：单一根目录、双后端（虚拟 / 真实磁盘）、每个插件一个私有沙箱。import { OSFS } from "../../src/javascripts/osfs.js"，或用全局 window.__osfs。

这是什么

访达里看到的 /文档、/下载、/桌面，背后是同一套 API。它有两个后端，插件代码不感知差别：

后端什么时候生效内容实际在哪
virtual（默认）用户没挂载真实文件夹；扩展形态（chrome-extension:// 没有目录选择器）恒是这个应用自己的 IndexedDB（库 webstartos-vfs，仓库 virtualfiles，keyPath: path）
disk用户授权过本地文件夹作根、且读写权限仍在那个真实文件夹，路径逐段映射；顶层骨架由内核预建

固定顶层目录（OSFS.TOP）

OSFS.TOP.documents.path   // "/文档"
OSFS.TOP.downloads.path   // "/下载"
OSFS.TOP.pictures.path    // "/图片"
OSFS.TOP.desktop.path     // "/桌面"
OSFS.TOP.trash.path       // "/废纸篓"  （internal: 预建骨架；内容可操作，夹本身受保护）
OSFS.TOP.appdata.path     // "/AppData" （internal: 插件私有数据区，不参与聚焦搜索）
别在代码里写 "/文档" 字面量——一律 OSFS.TOP.xxx.path（顶层目录名是系统决策，可能随语言/版本调整）。 也别自己造「虚拟目录层」：内核的树已能存目录行（OSFS.move / mkdir 都是真操作）。

插件私有数据（scope 沙箱）

const me = OSFS.scope("my-plugin");        // → /AppData/my-plugin
await me.ensure();                          // 预建 temp / config / data 三个子目录
await me.write("temp/draft.json", text);    // 临时产物
await me.write("config/layout.json", json); // 配置副本
await me.write("data/notes.md", body);      // 真实数据
await me.clearTemp();                       // 只清 temp

Deskly.fs 的九条沙箱方法（read / write / list / mkdir / remove / exists / stat / rename / copy）就是 scope(id) 的薄壳（见 Deskly）。 写文件自动补父目录，不必先 mkdir；rename 是同沙箱内移动，copy 的第二参是完整目标路径（不是父目录），目录会整棵递归复制。 另有 home() / temp()（免权限）与 at / writeAt / statAt / existsAt / mkdirAt / removeAt / renameAt / moveAt / copyAt / walkAt / watchAt 这组公开绝对路径方法（/AppData/<别人的id>/ 一律拒绝）。

五条约定（违反任何一条都会变成 bug）

  1. temp 不可依赖持久性：可能被手删、被「清空缓存」清掉、被浏览器回收。读不到就当缓存未命中，不许当错误，更不许当数据库。
  2. config 的真相源仍是 __settings（localStorage 槽）：冷启动要同步读的东西不能搬进文件；config/ 只放你主动写出的副本/导出，读它必须容忍缺失。
  3. 权限过期不静默回落：挂载存在但 readwrite 权限没批时，disk 后端调用抛 NeedsReauthError（按 err.name 判别，别匹配 message）。 界面要如实说「需要重新授权」，绝不写「已保存」——两个互相覆盖的真相比报错严重得多。
  4. unmount 只忘句柄不删盘：OSFS.unmount() 不删磁盘上任何东西；remove() 拒删根与顶层夹； 取消挂载也不会把内容搬回应用内根——文件留在那个文件夹里，重新挂载才看得见。
  5. 读路径有 1 秒元数据索引（metaIndex）：本标签页写入立即生效，另一个标签页最坏 1 秒后可见；写路径不受影响（一律回库确认）。

OSFS.mount() / reauthorize() 必须在用户手势里调（非手势上下文浏览器直接拒绝）。

顶层保护

/废纸篓 等 TOP 夹本身不可 remove / move（用户手建在根上的普通文件夹照删不误）；夹内内容操作（list / 写条目 / 删条目 / 递归删）正常。 UI 侧「删东西」的收口是 trash.js 的 moveToTrash() / emptyTrash()，业务代码不再直接调 OSFS.remove。
