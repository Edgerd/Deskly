应用商店与分发

商店界面里每个元素的真实含义、ZIP 安装的三级链路、禁用与还原、以及发布一个插件的完整流程。

界面语义（全部是真实数据，没有「推荐位」）

  • 卡片列表 = 注册表里全部插件（内置 + 已安装 ZIP），一个不多一个不少。
  • 分类过滤是真实语义：侧栏固定有「全部 / 内置 / 已安装 / 已禁用」四项，其余分类按各插件 store.category 聚合；没写 store 的插件只在「全部」里出现。
  • 详情页 = 插件自声明的 store 区块 + 权限栏。权限栏读 manifest.permissions，经 api-grants.describe() 出人类可读文案——和授权账本同源，不会出现「详情页说要文件权限、清单里却没声明」的对不上。
  • 「打开」调 load(插件id)；多应用套件落到 apps[0]。
  • 「禁用」不删文件：注册表打上 disabled 标记，程序坞 / 启动台灰显，重载扩展也不会复活它；再点「启用」即恢复。

ZIP 安装三级链（三级都成功才算装上，否则整体回滚）

  1. 读包：拖入 ZIP（或点「安装 ZIP…」）→ JSZip 解包（assets/vendor/jszip.min.js，按需加载）→ 校验： manifest 在包根或公共根、解包总字节 ≤ 10MB、id 合法且与目录结构一致。
  2. 落库：包内文件以 Blob 存进 IndexedDB（库 webstartos-plugins、仓库 installed，keyPath 为 id）—— 不会写进磁盘 mods/ 目录；注册表写入 _installed: true 标记。
  3. 接管验证：Service Worker（sw.js）负责拦截 ./mods/<id>/<file> 请求、从 IndexedDB 回源， 并在响应头写 X-Deskly-Plugin: <id>。安装器会真实请求一次验证这个头—— SW 没接管（比如首次安装 SW 还没 activate）就整段回滚，不留半装状态。
覆盖安装 同 id 再装一次 = 新包整体替换旧 Blob（按 id 整组换，不会有旧文件残留）， 商店记录安装历史与版本差异。用户此前「始终允许」的权限记录保留（账本按并集合并，绝不静默撤销）。

发布一个插件（完整流程）

  1. 在 mods/<id>/ 写完四个文件 + 图标（规范见插件包格式）。
  2. 内置发布：把 id 加进 plugin-manager.js 的 BUILTIN_IDS；第三方分发：不用动。
  3. 跑 node dev/static-check.mjs（第 6 节核对 manifest 声明的文件存在，第 7 节核对 permissions 三方对齐）。
  4. 导出：node dev/package-plugin.mjs <id> → dist/<id>-<version>.zip（打包即校验，少文件会在这一步就报错）。
  5. 交付：对方在应用商店里拖入 ZIP 或点「安装 ZIP…」。安装时系统展示权限清单请用户确认； 标记为敏感的权限在第一次调用时还会再弹一次「拒绝 / 仅此一次 / 始终允许」（机制见 Deskly 页权限账本，弹窗见 系统弹窗 dialog）。

禁用、卸载与「还原内置」

  • 禁用只是标记，文件与数据都在，随时启用。
  • 卸载 ZIP 插件：IndexedDB 里的 Blob 删除、注册表条目移除、权限账本清账（plugin-unregistered 广播触发）。
  • 内置插件文件打在扩展包里，用户删不掉——所以不存在「删了找不回」的内置；商店里的「还原内置」只是把同 id 的 ZIP 覆盖版移除，露出包内原版。
